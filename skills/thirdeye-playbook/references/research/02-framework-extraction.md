# 02-框架提炼

## 工程判断维度（4 个）

### 维度 1: 边界克制
**定义**：新方案应适配现有项目结构，不随意新增层或跨模块耦合，优先在现有模块边界内解决问题。

**证据场景**：
- `rule_architecture_boundary_001` 明确要求"新方案应适配现有项目结构"
- 模块划分清晰：`api/`（路由）、`services/`（业务）、`agents/`（Agent）、`schemas/`（模型）、`core/`（配置）
- 路由层仅负责编排，业务逻辑在服务层

**应用方式**：评审新方案时，先检查是否可复用现有模块；如需新增模块，必须说明边界理由。

**失效条件**：当现有模块确实无法承载新需求时，需明确说明边界扩展理由。

---

### 维度 2: 文档约束优先
**定义**：项目文档中声明的约束（MVP 范围、依赖版本、存储策略、术语定义）必须被明确处理，不能忽略或绕过。

**证据场景**：
- `README.md` 明确 MVP 范围边界（不包含 orchestrator composite 等）
- `CONTEXT.md` 统一术语定义
- `pyproject.toml` 精确锁定关键依赖版本
- `CLAUDE.md` 声明存储策略演进路径

**应用方式**：评审时逐项核对方案是否触碰文档约束；若触碰，需说明变更理由和迁移计划。

**失效条件**：当文档约束已过时或与新需求冲突时，需先更新文档再实施。

---

### 维度 3: 证据驱动
**定义**：所有结论必须有项目证据支撑，证据不足时明确标注"信息不足"，不臆造项目标准。

**证据场景**：
- `evidence_builder.py` 实现证据分级（confirmed/inferred/preference/unknown）
- `rule_honesty_boundary_001` 要求"缺乏证据时必须询问缺失信息"
- `review.py` 输出中包含 `missing_information` 字段

**应用方式**：评审时区分证据等级；对 `inferred` 和 `unknown` 级别的结论标注不确定性。

**失效条件**：当项目证据确实缺失时，应主动要求补充而非强行推断。

---

### 维度 4: 鲁棒性优先
**定义**：系统设计应优先保障可用性，对不稳定性因素（如 LLM 行为）设计回退路径。

**证据场景**：
- `sdk_runtime.py` + `review.py`/`distillation.py` 实现"SDK 优先 → 回退 deterministic"双模式
- 依赖精确锁定（`openai-agents==0.17.0`）避免 breaking change
- SecretScanner 保护敏感数据不入库

**应用方式**：评审新方案时，检查是否对关键路径设计了回退/降级机制；对 LLM 相关功能必须有确定性兜底。

**失效条件**：当性能/体验要求压倒鲁棒性时（如实时交互），需明确说明权衡理由。

---

## 决策启发式（8 条）

1. **如果新方案涉及新增模块** → 先检查现有模块是否可复用，必须说明边界扩展理由
2. **如果方案触碰文档约束** → 必须先更新文档再实施，不能绕过
3. **如果结论缺乏证据支撑** → 标注证据等级，要求补充信息
4. **如果涉及 LLM 调用** → 必须有确定性回退路径
5. **如果修改共享 schema** → 检查所有调用方，确保向后兼容
6. **如果新增依赖** → 优先评估现有依赖是否可替代，必须说明版本锁定策略
7. **如果涉及敏感数据处理** → 必须遵循 SecretScanner 规则，内容不入库
8. **如果变更存储策略** → 必须包含数据迁移方案

## 代码特征

| 特征 | 表现 |
|------|------|
| **命名习惯** | 模块名清晰（`project_scanner`, `evidence_builder`, `playbook_generator`），函数名动宾结构 |
| **抽象深度** | 适度抽象，服务层职责单一（SRP），避免过度抽象 |
| **状态策略** | 配置集中化（`Settings` 类），避免全局状态 |
| **错误处理** | 双模式回退（SDK → deterministic），证据不足时标注 `unknown` |
| **依赖偏好** | 精确版本锁定关键依赖，范围版本锁定次要依赖 |
| **测试观** | pytest 测试，MVP smoke test 作为端到端验证 |

---

## 评审特征

| 特征 | 表现 |
|------|------|
| **先抓什么** | 模块边界、文档约束、证据等级 |
| **容易否决什么** | 无证据支撑的架构变更、忽略文档约束的变更、未匹配测试风格的变更 |
| **如何表达拒绝** | 结构化输出：`severity` + `title` + `description` + `suggestion` + `evidence_ids` |

---

## 变更特征

| 特征 | 表现 |
|------|------|
| **改动粒度** | 按模块独立变更，避免跨模块耦合 |
| **测试先行** | 新特性需匹配现有 pytest 风格 |
| **风险推进** | 关键路径有回退机制，依赖变更需版本锁定 |

## 开发任务映射

### 1. 新功能开发
- **先读**：`README.md`（MVP 范围）、`CONTEXT.md`（术语）、相关 `services/` 模块
- **先问**：现有模块是否可复用？是否触碰文档约束？测试策略是什么？
- **倾向**：在现有模块边界内扩展，新增模块需说明理由
- **验证**：pytest 单元测试 + MVP smoke test
- **拒绝**：绕过文档约束、无测试覆盖、跨模块耦合未说明

### 2. Bug 修复
- **先读**：相关 `services/` 模块、`agents/` 模块、测试文件
- **先问**：Bug 根因是什么？是否影响核心路径？是否有回退方案？
- **倾向**：最小改动修复，优先修复而非重构
- **验证**：复现测试 + 回归测试
- **拒绝**：大范围重构式修复、未验证的修复

### 3. Code Review
- **先抓**：模块边界、文档约束、证据等级
- **先问**：是否符合 4 个工程判断维度？是否有测试覆盖？
- **倾向**：结构化评审输出，标注证据等级
- **验证**：对照 playbook 规则逐条检查
- **拒绝**：无证据支撑的结论、忽略约束的变更

### 4. 重构
- **先读**：相关模块代码、测试文件、文档约束
- **先问**：重构目标是什么？是否保持向后兼容？测试是否覆盖？
- **倾向**：按模块独立重构，保持接口稳定
- **验证**：全量测试 + smoke test
- **拒绝**：破坏接口稳定性的重构、无测试覆盖的重构

### 5. API 设计
- **先读**：`schemas/` 目录、相关路由文件、文档约束
- **先问**：API 是否遵循现有 schema 风格？是否向后兼容？是否有版本策略？
- **倾向**：遵循 Pydantic schema 风格，保持向后兼容
- **验证**：schema 验证 + 集成测试
- **拒绝**：破坏向后兼容的变更、无版本策略的 breaking change

### 6. 性能优化
- **先读**：相关 `services/` 模块、测试文件
- **先问**：性能瓶颈在哪里？优化是否影响鲁棒性？是否有测量数据？
- **倾向**：测量先于优化，优先优化热点路径
- **验证**：性能测试 + 回归测试
- **拒绝**：无测量数据的优化、牺牲鲁棒性的优化

---

## 反模式（5 条）

1. **绕过文档约束**：不更新文档直接实施变更
2. **无证据推断**：缺乏项目证据时强行得出结论
3. **跨模块耦合**：未说明理由的跨模块依赖
4. **LLM 无兜底**：关键路径依赖 LLM 但无回退机制
5. **依赖漂移**：不锁定关键依赖版本，随意升级

---

## 诚实边界

1. **单仓库局限**：本 Skill 基于 ThirdEye 项目本地代码，不保证适用于其他项目
2. **代码证据 vs 公开发言**：本项目无公开发言材料，所有结论来自代码和文档
3. **团队归因问题**：本项目为团队项目，无法区分个人风格与团队共识
4. **信息截止日期**：2026-05-19，后续变更可能改变工程判断
5. **MVP 阶段局限**：部分功能（如 PostgreSQL 存储）尚未实现，相关判断基于规划文档
