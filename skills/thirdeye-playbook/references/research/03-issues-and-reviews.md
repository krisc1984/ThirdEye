# 03-评审维度研究

## 评审标准推断

### 从现有代码和规则中提炼的评审关注点

1. **架构边界**（`rule_architecture_boundary_001`）
   - 新方案必须适配现有项目结构，不随意新增层或跨模块耦合
   - 关注：是否保持现有模块边界模型

2. **文档约束**（`rule_documented_constraints_001`）
   - 项目文档中声明的约束必须被明确处理
   - 关注：方案依赖或改变了哪些文档约束

3. **测试对齐**（`rule_test_strategy_001`）
   - 技术方案应识别与现有测试风格匹配的验证步骤
   - 关注：现有测试风格如何验证此变更

4. **工具链约束**（`rule_tooling_001`）
   - 构建、lint、运行时、打包配置应视为项目约束
   - 关注：方案是否更新或依赖现有项目工具链

5. **诚实边界**（`rule_honesty_boundary_001`）
   - 如果 playbook 缺乏证据，必须询问缺失信息而非臆造
   - 关注：结论是否有项目证据支撑

### 评审流程

```
Proposal → 匹配 playbook 规则 → 逐条检查 → 输出结构化评审结果
            ↓
         证据不足 → 标记 missing_information → 要求补充
```

### 拒绝标准

- 无证据支撑的架构变更
- 忽略 README/文档约束的变更
- 未匹配现有测试风格的变更
- 跨模块耦合未说明理由的变更
