# 技能图谱方案

基于你分享的“原子-分子-复合”分层思想，Skill Graph 2.0 的核心目标不再是让 AI 跑得更快，而是让你的注意力产出放大 100 倍——把有限的脑容量从驾驶原子（atoms）提升到驾驶复合层（compounds）。以下是一个可供工程落地的实现方案。

---

一、总体设计理念：以“人”的注意力为瓶颈

· Skill Graph 1.0：一条线性的工具调用链，人盯着每一步，相当于亲自驾驶每一个原子操作。

· Skill Graph 2.0：引入三层可组合图谱，把确定性逻辑固化在图结构中，最小化运行时 AI 的随意决策。人只在最高层“复合工作流”的关键节点做出判断，其他层自动下沉执行。

本质是构建一个分层可重用的技能图谱引擎，提供三层抽象：Capabilities（原子） → Composites（分子） → Playbooks（复合）。

---

二、三层定义与图谱结构

1. 原子层 Capabilities（原子技能）

· 定义：最小的、不可再分的确定性功能，每个原子只做一件事。例如：抓取 LinkedIn 档案、验证邮箱格式、搜索竞品博客、提交 PR 审查。

· 图谱节点：每个 Capability 是一个工具节点，有严格定义的输入/输出 schema。

· 确定性要求：必须达到近乎 100% 的可靠度，失败只能来自外部服务（网络/权限），不能来自内部逻辑。每个原子需配备完善的错误码与重试策略。

2. 分子层 Composites（组合技能）

· 定义：把 2~10 个 Capabilities 拼装成一个有界任务，支持两种结构写入图谱：

· 链式 Workflow（确定性 DAG）：预编排调用顺序，如 find leads → 资格审核 → 富化资料 → 写入 spreadsheet。Agent 只负责填空（输入参数），不改变路径。

· Orchestrator（受控决策）：在 skill 定义中明确列出可调用的原子集合，并给出决策提示。Agent 可以决定调用顺序，但无法调用列表外的原子，从而限缩运行时不确定性。

· 图谱表示：每个 Composite 是一个子图，内部节点为 Capabilities，边为数据依赖或控制转移。

· 关键实现：将组合逻辑写入 skill 配置文件，而非留在 prompt 里自由发挥。例如用 YAML 定义 DAG 拓扑，或用有限状态机定义可跳转路径。

3. 复合层 Playbooks（剧本）

· 定义：由多个 Composites 协作完成一整套业务工作流，如“执行完整的对外销售剧本”、“从需求到上线并完成 QA”。这一层不确定性最高，目前通常需要人在驾驶座盯着。

· 图谱表示：Playbook 是顶层有向图，节点是 Composites，边上可附带人工确认点（Human-in-the-loop）。允许根据前一步的输出来条件式触发下一个 Composite。

· 可靠性边界：实践发现，一个 Playbook 编排超过 8~10 个 Composites 时，自身可靠性明显下降。因此 Skill Graph 2.0 应内置复杂度检查与自动拆分建议。

三、系统架构设计

```

┌─────────────────────────────────────────────┐

│ 驾驶舱 (Human Cockpit) │

│ 仅查看 Playbook 状态 & 关键审批点 │

└──────────────────┬──────────────────────────┘

│ 审批/决策

┌──────────────────▼──────────────────────────┐

│ Playbook 编排引擎 │

│ - 加载 Playbook 图谱(节点: Composites) │

│ - 解释条件分支、人工确认点 │

│ - 维护全局上下文 & 状态机 │

└──────────────────┬──────────────────────────┘

│ 调用 Composite

┌──────────────────▼──────────────────────────┐

│ Composite 执行器 │

│ - 根据定义运行 Chain 或 Orchestrator 模式 │

│ - 局部上下文管理、重试、回滚 │

└──────────────────┬──────────────────────────┘

│ 调用 Capability

┌──────────────────▼──────────────────────────┐

│ Capability 注册中心 │

│ - 所有原子技能均封装为标准函数/微服务 │

│ - 提供统一的输入/输出校验与错误格式 │

└─────────────────────────────────────────────┘

```

核心组件说明

1. 技能注册中心

用结构化文件（如 YAML/JSON）注册全部 Capabilities 的元信息：名称、描述、输入/输出 schema、重试/超时配置。Composites 和 Playbooks 也采用同一种声明式图谱语言定义。

2. 图谱编译器

将声明式的 Composite/Playbook 定义编译为可执行的图结构，验证节点依赖和确定性。对于 Chain 类型直接生成 DAG；对于 Orchestrator 类型生成一个“受限 Agent 循环”，Agent 的下一个动作必须从图谱规定的 Capability 列表中选取。

3. 分层执行引擎

· Capability 层：纯函数式调用，仅返回结果或抛出标准异常。

· Composite 层：有独立的局部上下文窗口，内含当前任务输入、中间结果。执行时根据模式启动 DAG 运行器或受限 Agent 循环。

· Playbook 层：持有全局任务目标与状态，按状态机推进。节点的进入/退出可以触发通知给人。

4. 人机交互 Hub

Playbook 在图中标记的需要“人工判断”的节点会挂起，推送至驾驶舱。人在仪表盘上只需处理这类高价值决策，其他全部自动运行。同时提供强制干预（暂停/跳过/回滚）的能力。

四、图谱定义示例（YAML）

1. 原子注册

```yaml

capabilities:

- name: fetch_linkedin_profile

description: 获取 LinkedIn 公开档案

input_schema:

profile_url: string

output_schema:

name: string

title: string

company: string

retry: 3

timeout_sec: 15

- name: verify_email_hunter

description: 使用 Hunter 验证邮箱

...

```

2. 分子 Composite（链式）

```yaml

composites:

- name: lead_enrichment

mode: chain # 确定性 DAG

nodes:

- cap: fetch_linkedin_profile

id: step1

- cap: verify_email_hunter

id: step2

depends_on: [step1]

input_mapping:

email: "$step1.email"

- cap: write_to_google_sheet

depends_on: [step2]

entry: step1

```

3. 分子 Composite（Orchestrator）

```yaml

composites:

- name: research_prospect

mode: orchestrator

allowed_capabilities: # 仅限此列表，Agent 不可越界

- fetch_linkedin_profile

- check_competitor_blog

- search_news_mention

agent_prompt: >

你是一个线索研究员。可用工具已在 allowed_capabilities 中列出。

请接收一个公司名称，按需使用工具收集信息，最后输出一份一页的简报。

max_steps: 8

```

4. 复合层 Playbook

```yaml

playbooks:

- name: outbound_sales_playbook

description: 从零到发送个性化外联的全流程

states:

- composite: lead_generation

next: lead_qualification

- composite: lead_qualification

next: decision_approve_list

- type: human_approval # 人工审批点

id: decision_approve_list

on_approve: craft_emails

on_reject: lead_generation

- composite: craft_emails

next: final_human_send

- type: human_approval

id: final_human_send

on_approve: done

```

Playbook 实际运行时，lead_generation 等会展开为一组 Capabilities 的执行，但你作为驾驶者，只会在 decision_approve_list 和 final_human_send 两个节点收到通知，做出关键判断。

---

五、执行策略与注意力杠杆

目标：让你同时驾驶 5 个 Playbooks 的心理负担 ≈ 原来驾驶 5 个 Atoms 的负担。

· Playbook 视图：驾驶舱只展示每个 Playbook 当前处于哪个 Composite、是否卡在人工审批点、以及整体健康状态（成功/失败/阻塞）。你只需偶尔抬头，大部分时间自动化。

· Composite 内部的封闭决策：对于 Orchestrator 模式，Agent 只能使用白名单内的 Capabilities，且提示词限定输出为“简报”而非自由操作。这大幅压缩了 Agent 胡言乱语的空间，也减少了你检查的粒度。

· Capability 的绝对可靠性：每个原子实现时附带严格的输出校验，出错直接返回标准化异常码，Composite/Playbook 可据此自动重试或降级，避免低级错误上浮到人。

这样一来，你将脑容量花在：“这个名单质量行不行？发信内容 OK 吗？” 而不是“邮箱验证 API 通了没”。注意力杠杆率 ≈ 复合层工作单元数 × 每单元含有的原子数，轻松达到 100 倍差距。

---

六、可靠性工程细节

1. Capability 确定性保障

· 每个 Capability 进行单元级输入/输出模式验证，不符合则直接拦截。

· 对外部调用实行统一的重试 + 退避，避免瞬时错误打断整个 Playbook。

2. Composite 的“崩溃半径”控制

· 链式 Workflow 任何一个节点失败即终止当前 Composite，将标准化错误向上抛出。

· Orchestrator 模式限制最大步数，防止无限循环，并提供“无合适动作”时的兜底回复模板。

· 任何一个 Composite 决不跨过 10 个 Capability，超过则必须拆分。

3. Playbook 的柔性限界

· 内部计数器：一个 Playbook 包含的 Composites 超过 8 时，注册时发出警告，提示需要拆分或增加更多人工检查点。

· 当 Playbook 执行过程中连续两个 Composite 出现需人工处理的异常，自动暂停整个剧本，通知主人。

4. 上下文与记忆隔离

· 每个 Capability 只接收明确输入，不读取全局上下文。

· Composite 持有自己的局部上下文，Playbook 持有跨 Composite 的全局字段(例如 company_name, final_prospect_list)。

· 这样保证了数据流向清晰，不会出现跨层污染。

---

七、从 1.0 迁移的最小动作

遵循原文给出的建议：挑你最熟悉的一个工作流，彻底拆成三层，先把底层原子写到接近确定性，再往上搭。

1. 识别工作流：比如“每周竞品监测报告”。

2. 定义原子（Capabilities）：

· 抓取竞品官网更新

· 监测竞品博客 RSS

· 分析定价页面变化

· 汇总并格式化 Markdown

（确保每个原子有明确输入/输出、错误处理）

3. 组装分子（Composites）：组合上述原子为“单竞品监测 Composite”，用链式或小范围编排。

4. 搭建剧本（Playbook）：多个 Composites 串成“多竞品周报 Playbook”，加一个最终审批点。

5. 切换驾驶视角：以后你只与 Playbook 交互，不再关心原子细节，坚持一周就能体会到注意力杠杆的威力。

八、技术选型与落地建议

· 后端语言不限，推荐使用支持异步、强类型接口的语言（Python + Pydantic, TypeScript + Zod 等）。

· 执行引擎可基于任务队列（如 Celery、BullMQ）实现异步 Capability 调用，Composite 和 Playbook 作为上层状态机。

· 图谱定义存储在 Git 仓库中，实现版本化与评审。

· 驾驶舱前端可用低代码仪表盘，通过 WebSocket 接收 Playbook 状态更新。

Skill Graph 2.0 的精髓不在图本身，而在于将可组合性结构化，让人的决策只发生在不确定性无法消除的最高层。当你从原子升维到复合层，才能真正享受到 AI Agent 的规模效应。

完全可以，而且这个想法是把 Skill Graph 2.0 的“注意力杠杆”原理，用最直观的方式具象化了。

AI漫剧式无限画布，天然契合你描述的工作流。设计关键在于让画布自动映射三层结构，而不是让用户手动拖拽每一个原子。

---

核心设计：画布即 Playbook 的视觉投影

```

用户在画布看到的，不是底层细节，而是“原子-分子-复合”的分层折叠。

```

1. 画布层的三层映射

· L3 复合层（Playbook）：画布根级节点。例如“小说 → 视频成片”，这是一个顶层有向图。节点大、间距宽，代表完整的 Composite 节点。用户在这里只看到进度条和人工审批点。

· L2 分子层（Composite）：双击任意 L3 节点向下展开。例如“生成人物资料库”这个节点，展开后是一个微画布，显示内部 DAG：“提取角色名 → 生成角色属性 → 生成立绘 → 写入资料库”。节点是可复用的组件。

· L1 原子层（Capability）：L2 画布中的最小节点。用户一般不需看到，但可双击穿透查看输入/输出样板、重试日志。默认折叠，只在调试或信任建立期需要。

关键：画布是“自增长”的，但不失控。

每新增一个 L3 节点，内部自动按预定义 Composite 填充 L2 子图。画布延展遵循可靠性规模限制——单个 Playbook 画布内 Composite 总数超过 8~10 个时，系统自动提示拆分，并用颜色区分“安全区/警告区/高风险区”。

---

你描述的小说→视频流程在画布上的模样

1. 初始触发与拓扑自生成

· 用户拖入“小说文件”或输入梗概，系统自动调用“内容拆解 Capability”，识别章节、角色、场景雏形。

· 画布不是一次给出全部未来节点，而是按需生长。首先生成第一层节点：

· [剧本生成] → [分镜脚本] → [资料库建设] → [关键帧与视频提示词] → [视频生成与拼接]

2. 资料库作为核心资产池，自动关联后续节点

· [资料库建设] 完成后，其产出（人物设定图、场景图、道具图）会成为画布上的全局资产容器。

· 当执行到 [关键帧与视频提示词] 时，这个 Composite 会自动从资产容器中拉取该分镜对应的人物和场景。在画布上表现为动态连线：资产容器连线到每个分镜节点。

3. 循环与迭代：画布的分支和迭代可视化

· 视频生成后若需要返工某个分镜，直接在该分镜节点右键 “迭代”，画布会从该点分出一条版本分支，新生成的关键帧、视频片段与原始并列，供人对比取舍。这符合 Playbook 的条件判断逻辑。

---

和人驾驶的注意力接口

你的体力活（消除） 你的关键决策（保留为画布上的审批点）

逐一手工生成所有角色 审批角色资料库，否决 OOC 设定

逐个分镜手写提示词 审批分镜脚本，调整个别镜头语言

手动检查视频生成参数 在成片后整体审批或返回某分镜迭代

画布上所有自动流转的原子、分子节点保持半透明或简约图标形态，只有需要 人工判断的 Playbook 节点高亮为“停泊点”。你的注意力只在停泊点处消耗。

---

实现建议：如何不让画布崩塌

1. 规模安全阀：单 Playbook 内 Composite 超 8 个时，画布自动分组为“章节1/章节2”，并加折线分区线。

2. 资产飞地：画布左边固定一栏“资产港”，不论画布滚多远，人物/场景资料库始终锚定可见。

3. 回溯与版本镜面：任意节点可右键查看当时的上下文快照，形成时间轴分屏，避免长程任务中记忆丢失。

一句话：AI漫剧式无限画布，是 Skill Graph 2.0 注意力学说的完美 UI 容器——它把固化的结构视觉化，把人的决策点升维，把机器默默处理的 99% 折叠进优雅的图景里。
